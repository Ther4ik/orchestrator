# GARAZ Risk Orchestrator — MVP (backend + веб-интерфейс)

Прототип модуля-оркестратора для управления параллельными процессами оценки рисков: бесконфликтный запуск без взаимных блокировок и искажения данных при одновременной работе нескольких пользователей.

```
app/catalog.py        процессы, источники, веса, группы (из легенды)
app/models.py         Task, Source, Decision, статусы
app/orchestrator.py   диспетчер + Decision Engine (К-01…К-07)  <- главный файл, только stdlib
app/runner.py         имитация исполнения (asyncio), заменяется реальными расчётами
app/main.py           REST API (FastAPI) + раздача веб-интерфейса на /ui/
app/static/index.html веб-интерфейс (один файл, без сборки и зависимостей)
tests/                сценарии из описания конфликтов
demo.py               консольное демо с таймлайном
```

## Процессы MVP

В демо запускаются пять процессов — минимальный набор, на котором видно разрешение всех конфликтов К-01…К-07:

| Процесс | Вес | Что показывает |
|---|---|---|
| CR-01 — плановый расчёт ECL | средний | К-01 (хозяин конфликта, дубль), К-06 (сбой и повтор), К-02 (читает SRC-001) |
| CR-07 — внеплановый пересчёт ECL | средний | К-01: встаёт в очередь за CR-01 (одна группа ECL, одна дата) |
| MR-01 — расчёт VaR | средний | К-04: обновление SRC-006 во время расчёта; К-03: параллельно с CR-01 |
| LR-03 — анализ разрывов ликвидности | средний | К-05: ждёт готовности SRC-008; К-02: общие SRC-001/SRC-002 с CR-01 |
| MR-08 — экстренное стресс-тестирование | тяжёлый | К-07: лимиты нагрузки и приоритет экстренного запуска |

Остальные процессы из легенды (CR-02…CR-06, MR-02…MR-07, LR-01, LR-02, LR-04…LR-08) намеренно убраны из `app/catalog.py`.
Все 14 источников сохранены: каждый используется хотя бы одним из пяти процессов.

## Веб-интерфейс

Один файл `app/static/index.html`: чистые HTML/CSS/JS, шрифт Onest подключается с Google Fonts (без интернета используется системный). Бэкенд раздаёт его сам, адрес API подхватывается автоматически (тот же origin).

Данные обновляются опросом (polling) каждые 1,5 с: в бэкенде нет WebSocket/SSE, а этап имитации длится `STEP_SECONDS = 2.0`, так что прогресс, очередь и освобождение ресурсов видны «вживую».

| Экран                      | Что показывает и делает                                                                                   | Эндпоинты |
|----------------------------|-----------------------------------------------------------------------------------------------------------|-----------|
| Мониторинг                 | Состояние сервера, нагрузка (задачи / вес / тяжёлые / очередь), очередь с причинами ожидания (код К-xx, текст, блокирующая задача), таблица задач с прогрессом, «Отменить» / «Повторить», бейдж «источник обновился» | `/health`, `/system/load`, `/queue`, `/tasks`, `/tasks/{id}/cancel`, `/tasks/{id}/retry` |
| Запуск расчёта             | Выбор процесса (отдел, вес, группа, источники), дата, тип запуска, пользователь, имитация сбоя на выбранном этапе; вердикт `run` / `queue` / `reject` с причинами | `/processes`, `POST /tasks` |
| Карточка задачи            | Панель справа по клику на строку: версии источников на старте, staging, попытка, retry_of, ошибка, время | `/tasks/{id}` |
| Источники данных           | Статус, версия, читающие задачи, ожидание эксклюзивной записи; кнопки для демо: «Новая версия», «Эксклюзивно», смена статуса; подсвечены источники демо-сценариев (`DEMO_SOURCES` в `app/catalog.py`: SRC-001 → К-02, SRC-006 → К-04, SRC-008 → К-05), остальные приглушены | `/sources`, `POST /sources/{id}/update`, `PUT /sources/{id}/status` |
| Результаты и журнал        | Опубликованные результаты и таймлайн операций — доказательство порядка выполнения без конфликтов | `/results`, `/audit` |

Запуск интерфейса отдельно от бэкенда: откройте `app/static/index.html` с параметром `?api=http://localhost:8000` (CORS в API уже открыт).

### Сценарий демо
1. «Запуск расчёта»: плановый CR-01, затем ручной CR-07 за ту же дату → второй уходит в очередь (К-01), на «Мониторинге» видна причина и блокирующая задача.
2. «Источники данных»: «Новая версия» во время расчёта → у задачи появляется бейдж «источник обновился», а расчёт дочитывает зафиксированную версию (К-04).
3. «Источники данных»: «Эксклюзивно» → новые читатели ждут, пока освободятся текущие (К-02).
4. «Запуск расчёта» CR-01 с имитацией сбоя на этапе → «Ошибка», ресурсы освобождены, ожидавший CR-07 стартует сам, «Повторить» создаёт новую задачу (К-06).
   Статус источника SRC-008 → «Обновляется» и запуск LR-03 → ожидание, при «Готов» старт автоматически (К-05). Три запуска MR-08 за разные даты → третий ждёт (К-07).
5. «Результаты и журнал»: порядок событий на таймлайне.

## Как принимается решение (Decision Engine)
Запрос → проверки → `run` / `queue` (с причинами) / `reject`:
* дубль того же процесса за ту же дату → reject (К-01)
* источник в статусе «Ошибка» → reject; «Обновляется/Неполные» → queue (К-05)
* тот же расчёт (группа, напр. CR-01/CR-07) за ту же дату уже идёт → queue (К-01)
* источнику нужна эксклюзивная запись → новые читатели ждут (К-02)
* квоты: параллельных задач / суммарный вес / тяжёлых → queue (К-07)

Ресурсы выдаются пакетом «всё или ничего» → deadlock невозможен (К-03).
На старте фиксируются версии источников (К-04). Сбой → ресурсы освобождены, staging очищена, retry = новый ID (К-06).
Очередь сортируется по (приоритет, порядок поступления); при освобождении ресурса диспетчер сам запускает ожидающие.
